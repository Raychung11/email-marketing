Cron jobs for Hostinger  (hPanel → Advanced → Cron Jobs)
========================================================

Choose "Custom", not "PHP". PHP mode locks the command to /usr/bin/php, which
on Hostinger is 8.2 — too old for this application.

Both jobs are required, and there are exactly two. Do not add a third copy of
either "to make it faster" — sending the same campaign twice is a real outcome.

Replace the path below with your own. Get it by running `pwd` over SSH from the
application directory.


1. Scheduler — every minute
---------------------------
Starts due campaigns, advances journeys, retries failures, refreshes reports.
Every job inside takes a named expiring lock, so a minute that overlaps the
previous run cannot double-execute anything.

    /home/u822252863/domains/YOUR-DOMAIN/app/deploy/hostinger/cron-scheduler.sh


2. Queue worker — every minute
------------------------------
Does the actual sending, draining the queues in strict priority order so a
password reset never waits behind a 50,000-recipient campaign.

    /home/u822252863/domains/YOUR-DOMAIN/app/deploy/hostinger/cron-worker.sh


Set every dropdown — Minute, Hour, Day, Month, Weekday — to its "Every (*)"
option, or pick "Every Minute" from Common Settings.


Why scripts rather than the full command
----------------------------------------
Hostinger caps the command field at 255 characters and the worker command is
well past that. Putting it in a script is the better arrangement anyway: the
queue list and the flags sit in version control where they can be reviewed,
instead of in a panel text box nobody looks at again. The scripts also find a
PHP 8.3+ binary by checking its version rather than trusting a hardcoded path,
so a host that moves PHP does not silently stop your sending.


If your plan will not accept a one-minute schedule
--------------------------------------------------
Five minutes is fine. Edit deploy/hostinger/cron-worker.sh and change

    MAX_SECONDS="${MAX_SECONDS:-55}"   to   MAX_SECONDS="${MAX_SECONDS:-290}"

so the worker uses the whole gap instead of idling for four minutes in five.
The only effect is that a campaign scheduled for 10:00 may begin at 10:04.


Checking it works
-----------------
    tail -f storage/logs/scheduler.log
    tail -f storage/logs/worker.log

`php deploy/hostinger/preflight.php` fails if the scheduler has not run in the
last fifteen minutes, which is the fastest way to notice cron is not running at
all. Without cron the site still loads and still looks fine — it simply never
sends anything.

The scripts rotate their own logs once they pass 10MB, since shared hosting has
no logrotate.
